# Calculation API with 1C integration
## Русское руководство

### Краткое описание проекта

Данный проект предназначен для расчета стоимости стандартных и нестандартных изделий.

#### Возможности

- Расчёт себестоимости продукции
- Получение параметров из PostgreSQL
- Кэширование результатов в Redis
- Загрузка и обновление данных из Excel таблицы
- История изменений материалов и продукции

#### Стек

- Python 3.13
- FastAPI
- PostgreSQL 17
- Redis 8
- Alembic
- Docker Compose

#### Архитектура 

```text
app/
├── controllers/       # Обработка запросов и управление расчётами
├── data/              # Репозитории, схема БД, Redis и кэш
├── modules/           # Расчётные модули для серий продукции
├── logger/            # Настройка логирования
├── main.py            # FastAPI-приложение
└── schemas.py         # Схемы запросов и ответов

migrations/
└── versions/          # Миграции Alembic

tests/                 # Автоматические тесты
docker-compose.yaml    # API, PostgreSQL, Redis и миграции
```

## Быстрый запуск

#### 1. Подготовка окружения

Перед запуском требуется заполнить переменные окружения в `.env`.
Для копирования шаблона выполнить:

```bash
cp .env.example .env
```

Данный bash-скрипт скопирует содержимое шаблона .env.example и создаст .env файл, в который требуется подставить переменные окружения

##### 1.1 Переменные окружения

В проекте требуется заполнить всего 7 переменных:
```text
DB_IP - IP базы данных PostgreSQL, Пример: "postgres"
DB_PORT - Порт базы данных, Пример: 
DB_NAME - Имя базы данных
DB_USER - Имя пользователя, от лица которого будут выполняться запросы в БД
DB_PASS - Пароль от учетной записи пользователя

REDIS_URL=redis://redis:6379/0 - URL Redis-сервера (Изменять не требуется)
CALCULATION_CACHE_TTL=21600 - TTL кэша в секундах
```

#### 2. Запуск сервисов

Для запуска сервисов используется

```bash
docker compose up -d --build
```

После выполнения данной команды будут запущены следующие контейнеры:
* postgres
* redis
* migrate
* api


#### 3. Проверка состояния

Для проверки состояния используются слеующие команды:

```bash
docker compose ps # для проверки какие контейнеры в данный момент работают

docker compose logs <container_name> # для вывода журнала аудита контейнера

# Пример:
docker compose logs api

curl http://localhost:5433/ping # ping контейнера api, при успешном запросе должен вернуть ответ с сообщением "pong"
```
API будет доступен по адресу: 
http://localhost:5433/docs для ручного тестирования
А для отправки запросов:
http://localhost:5433

Для доступа с другого устройства в локальной сети вместо `localhost` требуется подставить ip устройства, на котором запущены сервисы.

Для доступа извне локальной сети требуется настройка обратного проксирования, и сертификаты безопасности, на данный момент не реализовано. (Думайте сами)

## Работа с API

#### Проверка доступности

Для проверки доступности API, можно отпавить GET- запрос на `/ping` эндпоинт, при успешной проверке ответ сервиса должен быть: "pong"

#### Расчёт стоимости

Для расчёта стоимости изделия требуется отправить POST-запрос на `/calculate` и указать в теле запроса серию в поле `series` и параметры в поле `parameters`

Формат запроса:

```json
{
    "series": "Название серии",
    "parameters": "Параметры изделия"
}
```

Пример запроса:
```json
{
    "series": "Стеллаж СтПП",
    "parameters": "600/600/1800/RAL7024/н.ст.08/-/4/СССС/усиление.нет/разборн./ст.опоры"
}
```

Пример ответа:
```json
{
    "cost": 12345,
    "markup": 1.5
}
```

## База данных

База данных содержит следующие основные таблицы:
- products, где хранятся данные о товарах, а именно серия, тип продукции, полное название изделия
- materials, где хранятся все материалы для расчета стоимости изделий
- materials_for_products, где хранятся отношения товаров и материалов используемых для расчета
- product_mapping, где хранятся записи о точных названиях динамически подгружаемых расчетных модулей
- product_categories, где хранится информация о категориях изделий
- calculated_products, где хранятся стоимости стандартных изделий, полученные из прайс-листа в excel

### Миграции

#### Текущая версия

```bash
docker compose run --rm api alembic current
```

#### Применить миграции

```bash
docker compose run --rm api alembic upgrade head
```

#### Создание миграции

Для создания миграции следует для начала изменить `app/data/database_schema.py`, а затем заполнить:

```bash
docker compose run --rm api \
    alembic revision --autogenerate -m "описание изменения"
```

#### Проверка расхождения

Для проверки расхождений выполнить: 

```bash
docker compose run --rm api alembic check
```

#### Откатить последнюю миграцию

Для отката последней миграции выполнять: 

```bash
docker compose run --rm api alembic downgrade -1
```

## Частые проблемы

#### API не запускается

Прежде всего в таком случае нужно проверить логи контейнеров, а именно API, и миграций:
```bash
docker compose logs api 
docker compose logs migrate 
```

#### PostgreSQL недоступен

```bash
docker compose exec postgres pg_isready
```

#### Redis недоступен

```bash
docker compose exec redis redis-cli ping
```

#### Схема базы не соответствует метаданным(metadata) 

```bash
docker compose run --rm api alembic check
```

#### Памятка по безопасности
- НЕ добавлять .env файл в git. [1]
- Использовать отдельные учетные данные на сервере
- Использовать отдельные учетные данные для запросов API в БД. Разрешение только на чтение [2]
- Не публиковать дампы базы данных



1. Так как этот файл содержит переменные окружения, в том числе пароль от базы данных, имя пользователя, ip базы данных, данный файл НИ В КОЕМ СЛУЧАЕ не должен попасть в git проекта.

Почему так важно не добавить .env в git? Всё просто, при добавлении в гит этого файла, сохраняется его история (в случае добавления в гит готового файла из него записывается добавление всех строк). Даже при добавлении этого файла в приватный репозиторий мы не обезопасим наши данные, т.к. в какой-то момент вы можете забыть о том что там хранятся чувствительные данные или решите поделиться этим проектом с кем-то еще через github и сделаете репозиторий приватным, в этом случае любой пользователь github в теории сможет найти пароль от базы данных, пользователя, и пр. через строку поиска в github

2. Данное ограничение нужно для того, чтобы обезопасить систему от SQL-инъекций и других типов атак. При таком подходе система не сможет сама удалять или изменять данные в базе данных, только получать их.


# English guide

## Database migrations

Database schema changes are managed by Alembic. The connection is assembled
from `DB_IP`, `DB_PORT`, `DB_NAME`, `DB_USER`, and `DB_PASS`; credentials are
not stored in `alembic.ini`.

Docker Compose runs `alembic upgrade head` in the one-shot `migrate` service
before starting the API:

```bash
docker compose up -d --build
```

Useful commands:

```bash
# Show the database revision
docker compose run --rm api alembic current

# Check whether model metadata and the database schema differ
docker compose run --rm api alembic check

# Generate a migration after changing app/data/database_schema.py
docker compose run --rm api alembic revision --autogenerate -m "describe change"

# Apply pending migrations manually
docker compose run --rm api alembic upgrade head

# Roll back one revision
docker compose run --rm api alembic downgrade -1
```

Review every autogenerated migration before applying it. `alembic stamp` is
only for adopting a pre-existing schema; do not use it to initialize a new,
empty database.
